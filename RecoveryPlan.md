# Recovery Relay — Hackathon MVP Development Plan

## MVP goal

The first test proves one complete recovery-support loop:

**A patient receives a medication reminder, follows a rehabilitation exercise video, encounters a difficulty, gets support from a Recovery Twin, requests clinical help, and receives a response from the healthcare team.**

The clinician can also see whether the patient is following the assigned medication and exercise schedule.

Everything in this plan serves that loop for **one scenario: recovery after knee replacement surgery**.

### Assumptions

- Mobile app: **Expo + React Native + TypeScript**.
- Backend: developer's choice. The shared contract is REST + JSON.
- Clinical dashboard: simple web application.
- Existing questionnaires are already implemented. **Do not rebuild them.**
- No AI, real zVEM integration, or production authentication.
- Demo login uses seeded accounts.
- All patient-facing text is in **Slovenian**. Code, API fields, and clinical dashboard can be in English.
- Use synthetic patient data only.
- Medication schedules and exercise instructions are predefined demo data, not generated by the app.
- Exercise videos are pre-recorded and hosted as static files.
- Medication reminders use local device notifications.
- Both mobile and backend teams develop against the same API contract. Mobile can use fixture JSON until the API is ready.

# Shared contract

Agree on the data model, API, and status transitions before implementation.

## 1. Data model

| Entity          | Key fields                                                                                  | Notes                                              |
| --------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| User            | id, name, alias, role, language                                                             | Roles: patient, twin, clinician                    |
| Episode         | id, patientId, procedureKey, startDate, durationDays, timezone                              | One recovery period per patient                    |
| Medication      | id, episodeId, name, doseLabel, instructions, timesLocal[]                                  | Prescribed schedule, seeded for demo               |
| MedicationEvent | id, medicationId, scheduledFor, status, recordedAt                                          | Status: taken, skipped                             |
| Exercise        | id, episodeId, title, instructions, videoUrl, repetitions, frequencyPerDay                  | Assigned rehabilitation activity                   |
| ExerciseEvent   | id, exerciseId, scheduledFor, status, recordedAt                                            | Status: completed, having_trouble                  |
| TwinProfile     | userId, procedureKey, recoveryStage, language, bio, available                               | Public peer-support profile                        |
| TwinMatch       | id, episodeId, twinUserId, status, createdAt, endedAt                                       | Status: proposed, active, ended                    |
| PeerMessage     | id, matchId, senderId, body, createdAt                                                      | Private patient–Twin messages                      |
| PeerReport      | id, matchId, reporterId, reason, createdAt                                                  | Report inappropriate conversations                 |
| Consent         | id, userId, scope, acceptedAt, revokedAt                                                    | Peer participation and chat consent                |
| CareCase        | id, episodeId, origin, contextType, contextId, frictionType, description, status, createdAt | Structured clinical handoff or clinician follow-up |
| CareMessage     | id, caseId, senderId, body, createdAt                                                       | Clinical team ↔ patient                            |
| CaseStatusEvent | id, caseId, oldStatus, newStatus, actorId, createdAt                                        | Status history                                     |

### Important rules

- A patient can have only **one active Recovery Twin match** in the MVP.
- A medication dose is uniquely identified by `medicationId + scheduledFor`.
- An unconfirmed medication dose is **not automatically classified as skipped**.
- Peer chat messages are never automatically copied into a clinical case.
- A patient must confirm a patient-initiated clinical handoff before submission.
- Only clinicians can create clinical responses or initiate clinician follow-up cases.
- Existing questionnaire data remains in its current implementation.

| Endpoint                           | Used by      | Returns / Action                |
| ---------------------------------- | ------------ | ------------------------------- |

| POST /twin-matches/:id/report      | Patient/Twin | Reports a conversation          |

### Clinical handoff and communication

| Endpoint                       | Used by     | Returns / Action                                |
| ------------------------------ | ----------- | ----------------------------------------------- |
| POST /episodes/:id/cases       | Patient app | Creates a structured clinical handoff           |
| GET /episodes/:id/cases        | Patient app | Cases, statuses, and clinical responses         |

All endpoints must check the user's role and whether they are allowed to access the requested patient, match, or case, even with demo authentication.

## 4. Status definitions

### Medication

- **Scheduled:** dose is due but has no recorded outcome.
- **Taken:** patient explicitly marked it as taken.
- **Skipped:** patient explicitly marked it as skipped.
- **Unconfirmed:** scheduled time has passed, but the patient has not recorded an outcome.

The UI must distinguish **Skipped** from **Unconfirmed**.

### Exercises

- **Not Started**
- **Completed**
- **Having Trouble**

### Clinical cases

1. **Submitted:** patient has requested help, or clinician has opened a follow-up.
2. **In Review:** clinician has opened the case.
3. **Awaiting Patient:** clinician has responded and is waiting for confirmation.
4. **Resolved:** patient confirms the issue is resolved.

If the patient selects **Still Need Help**, the case returns to **In Review**.

## 5. Clinical triage columns

The dashboard contains four columns.

**Needs Attention**

- Newly submitted patient handoffs.
- Patients with an adherence concern that has not yet been reviewed.

**In Review**

- Cases claimed by the clinical team.

**Awaiting Patient**

- Cases where the clinical team has responded and is waiting for patient confirmation.

**On Track**

- Patients without open cases or current adherence concerns.

### MVP adherence rules

Use simple, deterministic rules to surface potential follow-up needs:

- Two explicitly skipped medication doses within 48 hours → nonurgent adherence concern.
- An exercise marked `Having Trouble` → visible in the patient's activity history.
- Two consecutive days with exercises explicitly marked `Having Trouble` → nonurgent adherence concern.
- A submitted patient handoff → immediately appears in **Needs Attention**.

These thresholds are **demo configuration only**, not clinically validated escalation rules.

An unrecorded dose or exercise must not be treated as proof of non-adherence.

The system does not automatically diagnose complications, change treatment, or provide dosage instructions.

# Backend and dashboard plan

Build in the following order.

## Step 1 — Scaffold and seed

Create:

- Backend API and database.
- Data model from the shared contract.
- One knee replacement recovery plan.
- One primary patient.
- Three Recovery Twin profiles.
- One clinician account.
- Sample medication and exercise records.
- A demo reset script.

Seed additional patients only if needed to populate the dashboard.

## Step 2 — Demo authentication

Implement `POST /auth/demo-login`.

Provide predefined accounts:

- **Patient:** Maja
- **Recovery Twin:** Ana
- **Clinician:** Dr. Novak

No passwords required.

Each role must see only its own permitted screens and data.

## Step 3 — Recovery plan API

Implement the endpoints that return:

- Recovery day.
- Medication schedule.
- Exercise schedule.
- Exercise video URLs.
- Recorded medication and exercise progress.

The patient app should be able to render the entire recovery plan from this response.

Do not modify the existing questionnaire implementation.

## Step 4 — Medication adherence

Implement medication event recording.

Requirements:

- Save `Taken` or `Skipped` against a specific scheduled dose.
- Prevent duplicate records for the same dose.
- Allow correcting a previously recorded status.
- Return today's medication status.
- Provide adherence information to the clinician dashboard.

For the MVP, the clinician should see counts and individual dose statuses rather than a complex adherence score.

## Step 5 — Exercise progress

Implement exercise event recording.

Requirements:

- Store `Completed` or `Having Trouble`.
- Associate each event with an assigned exercise.
- Store the date and time.
- Return exercise history to the patient app and dashboard.

The video files themselves can be served statically. No video processing service is needed.

## Step 6 — Recovery Twin matching

Implement a simple rule-based matching function.

**Matching inputs:**

- Same procedure or recovery category.
- Compatible language.
- Twin availability.
- Prefer a Twin who is further along in recovery.

**Matching output:**

- One suggested Twin.
- Alias.
- Recovery experience.
- Short profile description.

Only profiles with valid participation consent are eligible.

No machine learning or recommendation model is needed.

## Step 7 — Twin chat

Implement:

- Send message.
- Retrieve conversation.
- End match.
- Report conversation.

Use simple polling every few seconds instead of WebSockets if that is faster to implement.

Store chat messages separately from clinical messages.

**Do not automatically share peer chat content with clinicians.**

## Step 8 — Structured handoff

When the patient selects **I Need Help**, generate a clinical case using structured fields.

Example:

```json
{
  "episodeId": "episode-1",
  "origin": "patient_friction",
  "contextType": "exercise",
  "contextId": "ex-1",
  "frictionType": "fear_or_uncertainty",
  "description": "I am afraid to perform this exercise because of pain.",
  "confirmedByPatient": true
}
```

The patient must preview and confirm the request.

Once submitted:

- Save the case.
- Set status to `Submitted`.
- Make it visible in the clinician triage queue.
- Show the request in the patient's clinical support section.

## Step 9 — Clinical triage API

Implement `GET /staff/triage`.

Group patients into the four defined columns.

Each patient card should show:

- Patient name.
- Procedure.
- Recovery day.
- Latest issue or adherence concern.
- Case status.
- Time since submission.

No AI summaries are needed.

## Step 10 — Clinical dashboard

Build two screens.

### Screen A — Triage Queue

Four columns:

- Needs Attention
- In Review
- Awaiting Patient
- On Track

Clicking a patient opens their profile.

### Screen B — Patient Profile

Display:

- Patient and recovery details.
- Medication adherence summary.
- Exercise completion history.
- Open clinical cases.
- Patient-reported barriers.
- Clinical message history.

Provide two primary actions:

- **Review / Respond**
- **Start Follow-up**

The clinician must be able to identify why a patient is struggling without reviewing every individual interaction.

## Step 11 — Clinical response and resolution

Implement:

- Claim a case.
- Send a clinical response.
- Move case to `Awaiting Patient`.
- Display the response in the patient app.
- Allow patient to select `Issue Resolved` or `Still Need Help`.
- Update the case status accordingly.

Preserve case status history.

## Step 12 — Deployment

Provide:

- Reachable backend URL.
- Reachable clinical dashboard.
- Mobile app connected to the same backend.
- Demo reset mechanism.

The full flow must work across devices without editing the database manually.

# Patient mobile app plan

## Screen 1 — Recovery Home

Display:

- Recovery day.
- Today's medication reminders.
- Today's rehabilitation exercises.
- Recovery Twin shortcut.
- Clinical support shortcut.
- Overall activity completion.

Primary purpose: show the patient what they need to do today.

## Screen 2 — Medication Schedule

Display:

- Medication name.
- Prescribed dose label.
- Scheduled time.
- Instructions.
- Status: Scheduled, Taken, Skipped, or Unconfirmed.

Actions:

- **Mark as Taken**
- **Mark as Skipped**
- **I Have a Problem**

Selecting **I Have a Problem** opens the Friction Selector with the medication preselected.

### Medication notifications

- Request notification permission.
- Schedule local reminders at the configured medication times.
- Tapping a notification opens the relevant medication.
- Reschedule notifications when the schedule changes.
- Cancel relevant notifications when the user logs out or the schedule is removed.
- Provide an in-app reminder fallback when notification permission is denied.

Add a **Trigger Demo Reminder** button in development mode so the reminder can be demonstrated reliably.

Do not provide advice to double doses or change medication schedules.

## Screen 3 — Rehabilitation Exercises

Display assigned exercises as cards.

Each card includes:

- Exercise title.
- Demonstration video.
- Written instructions.
- Repetitions.
- Recommended frequency.
- Completion status.

Actions:

- **Watch Video**
- **Mark Completed**
- **Having Trouble**

The video player must support play, pause, and replay.

Selecting **Having Trouble** opens the Friction Selector with the exercise preselected.

Use one or two preapproved demonstration videos for the MVP.

## Screen 4 — Recovery Twin Matching

Display:

- Suggested Recovery Twin.
- Alias.
- Similar recovery experience.
- Recovery stage.
- Short introduction.

Actions:

- **Connect with Twin**
- **Decline**

Before connecting, show a brief consent screen explaining what the Twin can see.

## Screen 5 — Recovery Twin Chat

Implement:

- One-to-one text chat.
- Conversation history.
- Message timestamps.
- Clear distinction between sender roles.
- Button to request clinical help.
- Report conversation.
- End connection.

Show a visible boundary statement:

**"Your Recovery Twin shares personal experience and emotional support. Medical decisions belong to your healthcare team."**

Do not attempt automatic medical advice detection in the MVP.

## Screen 6 — Recovery Friction Selector

Allow patients to report what is preventing them from following their recovery plan.

Categories:

- Pain or physical discomfort
- Fear or uncertainty
- Lack of motivation
- Difficulty understanding instructions
- Medication-related difficulty
- Transportation or logistics
- Other

The screen must:

- Identify the related medication or exercise.
- Allow selection of a barrier.
- Allow an optional written explanation.
- Show a preview of the clinical request.
- Require confirmation before submission.

Primary action: **Send to Care Team**.

## Screen 7 — Clinical Support

Display:

- Submitted requests.
- Current status.
- Clinical team responses.
- Date of last update.

Actions:

- **Issue Resolved**
- **Still Need Help**

A response from the clinician must appear here, not in the private Twin chat.

# Recovery Twin app plan

For the MVP, the Twin uses the same mobile app with a different role.

## Twin Home

Display:

- Active patient connection.
- Patient alias.
- Shared recovery category.
- Open chat button.

## Twin Chat

Allow:

- Sending and receiving messages.
- Viewing chat history.
- Reporting inappropriate messages.
- Ending a connection.

Do not show:

- Patient medication schedule.
- Questionnaire answers.
- Clinical cases.
- Full medical history.
- Clinician responses.

The Twin is a peer-support participant, not a member of the clinical team.

# Definition of Done

The hackathon MVP is done when:

1. A patient can see their assigned recovery plan.
2. Medication reminders work, and doses can be recorded.
3. Rehabilitation videos play, and exercises can be marked completed or problematic.
4. A patient can connect with a Recovery Twin and exchange messages.
5. A patient can submit a recovery barrier as a structured clinical request.
6. A clinician can see both the request and relevant adherence information.
7. A clinician can respond to the patient.
8. The patient can confirm that the issue is resolved.
9. The clinical dashboard reflects the updated status.
10. The entire demonstration can be reset and repeated reliably.

**Core product principle:** Recovery Relay connects everyday recovery activities, human peer support, and clinical follow-up in one continuous patient journey.

The MVP should demonstrate that connection—not attempt to build a complete hospital information system.

**Safety boundary:** This is a prototype using synthetic data. It is not suitable for real clinical deployment without validated care protocols, appropriate emergency guidance, authentication, data protection controls, and clinical oversight.
